# Руководство по внесению изменений в MyInvestor

Добро пожаловать в проект! Этот документ описывает процесс разработки, соглашения по работе с Git и структуру репозитория, чтобы новые файлы и папки были понятны и не нарушали общую архитектуру проекта.

## 📁 Структура проекта

На текущий момент репозиторий содержит базовую структуру Go-приложения:

```text
MyInvestor/
├── cmd/
│   └── api/
│       └── main.go                # точка входа приложения
├── internal/
│   ├── handler/                   # HTTP-обработчики
│   ├── repository/                # работа с данными и внешними системами
│   └── service/                   # бизнес-логика
├── pkg/
│   └── config/                    # общие конфиги и утилиты
├── .air.toml
├── .dockerignore
├── .gitignore
├── CONTRIBUTING.md
├── Dockerfile
├── README.md
├── docker-compose.yml
├── go.mod
└── tmp/                            # временные файлы Air (игнорируются Git)
```

Важно:
- `cmd/api` — единственная точка запуска сервиса.
- `internal` — всё, что относится к доменной логике, обработчикам и хранилищам.
- `pkg` — переиспользуемые компоненты и конфиги.
- Папки в `internal/` и `pkg/` могут быть пустыми на старте, но их не следует создавать хаотично: каждая новая директория должна иметь понятную ответственность.

---

## 📋 Основные принципы

1. **Каждая задача = новая ветка = новый Pull Request**
2. **Никаких коммитов напрямую в `main` или `develop`** — только через PR
3. **Code Review обязателен** — изменения должны быть проверены до merge
4. **Каждый PR должен быть связан с задачей** — в описании или комментарии указываем задачу/issue
5. **Новые файлы и папки создаются по структуре проекта** — без бессистемных "временных" директорий

---

## 🌿 Ветвление (Git Flow)

Используем следующую схему:

- **`main`** — стабильная версия проекта
- **`develop`** — текущая разработка
- **`feature/*`** — ветки для отдельных задач

Если ветки `develop` ещё нет, сначала согласуйте с командой целевую ветку и используйте её вместо `develop` в инструкциях ниже. Код в защищённые основные ветки попадает только через PR.

---

## 📝 Именование веток

Формат: `feature/username/GO-<номер-задачи>_краткое_описание`

Примеры:
```bash
feature/maksim/GO-1_add_main_screen
feature/alex/GO-5_implement_csv_parser
feature/ivan/GO-12_fix_dividend_calculation
```

Правила:
- Вместо `username` указываем своё имя или ник
- Номер задачи берём из таск-трекера/issue
- Описание пишем на английском, через подчеркивание
- Не используем пробелы, кириллицу и спецсимволы

## 🔄 Процесс работы над задачей

### Шаг 1: Создай ветку от `develop`

Обнови ссылки на удалённые ветки и создай feature-ветку от актуальной `develop`:

```bash
git fetch origin
git checkout -b feature/your_name/GO-12_task_description origin/develop
```

Если ветки `origin/develop` нет, согласуй с командой целевую ветку и подставь её вместо `origin/develop` в инструкциях ниже. Эти команды Git одинаковы в терминалах Windows, macOS и Linux.

### Шаг 2: Работай локально и фиксируй изменения

```bash
git add .
git commit -m "GO-12: add dividend calculation logic"
git push origin feature/your_name/GO-12_task_description
```

### Шаг 3: Перед созданием PR — синхронизируйся с `develop`

```bash
git fetch origin
git checkout feature/your_name/GO-12_task_description
git merge origin/develop
git push origin feature/your_name/GO-12_task_description
```

Если команда предпочитает rebase, вместо `git merge origin/develop` выполни `git rebase origin/develop`. Используй только один способ синхронизации. Если возникли конфликты, разреши их, проверь изменения и заверши операцию до отправки ветки.

### Шаг 4: Создай Pull Request

- **From:** `feature/your_name/GO-12_task_description`
- **To:** `develop`

### Шаг 5: Заполни описание PR

В PR обязательно указываем:
- что именно изменили;
- какие файлы затронуты;
- как проверяли;
- ссылки на задачу/issue, если они есть.

### Шаг 6: Дождись review и исправь замечания

После проверки код-ревьюером вносим правки, повторно проверяем и обновляем PR.

### Шаг 7: Merge после апрува

Merge выполняет тот, кто отвечает за ветку или reviewer с доступом к репозиторию.

## 🧱 Правила по созданию новых файлов и папок

При добавлении нового кода придерживаемся следующей схемы:

- `cmd/api/` — только точка запуска приложения
- `internal/handler/` — HTTP и API-обработчики
- `internal/service/` — бизнес-логика и сценарии использования
- `internal/repository/` — работа с БД, репозиториями, внешними API
- `pkg/` — общие компоненты, configuration, helpers, utilities

Рекомендации:
- Не создавай папки ради "на будущее" без конкретного назначения
- Если файл относится к HTTP-слою, кладём его в `internal/handler/`
- Если это логика работы с данными — в `internal/repository/`
- Если это общий reusable код — в `pkg/`
- Не смешивай разные ответственности в одном файле без необходимости

## 🧪 Локальная проверка

Команды ниже одинаковы на Windows, macOS и Linux и выполняются из корня репозитория. Перед PR запусти тесты:

```bash
go test ./...
```

Для проверки API запусти backend по инструкции в [README.md](./README.md) через Air и открой `http://localhost:8080/api/v1/health` в браузере. Ожидаемый ответ:

```json
{"status": "ok", "app": "MyInvestor"}
```

PostgreSQL для текущей версии API необязателен, поскольку приложение пока не подключается к базе. Если Docker установлен и для задачи нужна локальная база, запусти контейнер:

```bash
docker compose up -d
```

Остановить её можно командой:

```bash
docker compose down
```

## ⚠️ Частые ошибки

### 1. Работа без ветки
**Симптом:** изменения идут напрямую в `main`/`develop`.
**Решение:** всегда создаём `feature/*` ветку и PR.

### 2. Не синхронизировали ветку с `develop`
**Симптом:** появляются конфликты и старые версии кода.
**Решение:** перед PR выполняем `git merge develop` или `git rebase develop`.

### 3. Создаёшь "лишние" папки и файлы
**Симптом:** проект разрастается хаотично.
**Решение:** придерживаемся структуры `cmd`, `internal`, `pkg` и не создаём директории без роли.

### 4. Пустой PR без описания
**Симптом:** ревьюеру трудно понять, что и зачем менялось.
**Решение:** всегда заполняем шаблон PR полностью.

### 5. Застрял и молчишь
**Симптом:** задача висит и не двигается.
**Решение:** если проблема не решается больше 1 часа — писать в общий чат и просить помощь.
